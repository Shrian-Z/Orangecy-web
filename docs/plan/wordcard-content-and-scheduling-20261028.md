# Orangecy 词卡内容与智能调度计划书

日期：2026-10-28  
状态：研究 / 计划，不含代码改动。  
目标：回答两个问题——**ECDICT 够不够撑起主流级词卡？抖音式分发能不能和记忆调度融合？**

---

## 0. 一页结论

1. **ECDICT 够做“词典骨架”，不够做“完整词卡”。**  
   它覆盖了现有三本词书的全部单词，释义、音标、词频、考试标签、词形变化都有；但没有例句、音频、搭配、词根、助记、图片，也没有“选哪个义项”的教学层。

2. **词卡的差距不在词数，而在“一词一条内容”。**  
   770,611 条词条不等于 770,611 张能教人的卡。主流 App 的护城河是**每个词的核心义、例句、音频、搭配、考义和难度**，不是词典收词量。

3. **抖音式算法可以融合，但只能融合在“分发层”，不能替代“记忆层”。**  
   FSRS 决定“哪些词该复习”；分发模型决定“这次用哪首歌、哪条例句、哪种题型把它端上来”。  
   北极星指标必须是**延迟回忆**，不是停留时长。

4. **真正的护城河不是调度算法。**  
   FSRS 开源，排序模型可买可抄；难复制的是：**词—歌词—音频—用户偏好—长期回忆数据的上下文图谱**，以及内容授权和用户自己的词书/歌单。

5. **MVP 不需要深度学习。**  
   FSRS + 三键评分 + 当天修复 + 3,000–5,000 张人工审核的核心卡 + 一个规则/bandit 分发器，已经能验证核心假设。  
   先证明“歌词语境能提高延迟回忆”，再谈大模型。

## 1. ECDICT 审计

### 1.1 数据规模与字段完整度

审计对象：GitHub 默认 `ecdict.csv`（约 63 MB，770,611 行）。

| 字段 | 非空数量 | 占比 | 判断 |
|---|---:|---:|---|
| word | 770,611 | 100% | 词条齐全 |
| translation | 770,238 | 99.95% | 中文释义几乎全覆盖 |
| phonetic | 218,065 | 28.3% | 全库偏低，但目标词书约 99% |
| definition | 160,884 | 20.9% | 英文释义约两成，目标词书约 99.9% |
| pos | 0 | 0% | 默认 CSV 为空；只能从 translation 前缀解析 |
| collins | 13,633 | 1.8% | 只是星级，不是完整柯林斯词典 |
| oxford | 3,461 | 0.45% | 牛津 3000 核心标记 |
| tag | 14,942 | 1.94% | 考试标签，覆盖不均 |
| exchange | 96,290 | 12.5% | 词形变化/lemma，很有用 |
| detail | 约 0 | 0% | 官方标注“例句待添加” |
| audio | 0 | 0% | 没有音频 URL |

数据结构上还有两个容易被忽略的问题：

- **phrase 很多**：366,599 条含空格，81,553 条首字母大写，57,950 条带连字符，92,302 条长度超过 20 字符。  
  它是词典，不是干净的“单词书”；直接全量制卡会混进大量短语、专名、变体。
- **translation 有大量领域噪声**：约 381,627 条（49.5%）含 `[医] [经] [计] [化]` 等领域标记。  
  对词典是优点，对词卡是干扰；必须清洗、选义、重排。

### 1.2 对现有三本词书的覆盖

用仓库里的 `cet4` / `cet6` / `gaozhong` 词书逐词比对：

| 指标 | CET4（4,542） | CET6（3,991） | 高中（3,738） |
|---|---:|---:|---:|
| ECDICT 命中 | 4,542 / 100% | 3,991 / 100% | 3,738 / 100% |
| 中文释义 | 100% | 100% | 100% |
| 英文释义 | 99.9% | 99.8% | 99.7% |
| 音标 | 99.6% | 99.3% | 98.9% |
| collins 星级 | 92.9% | 88.1% | 92.1% |
| oxford 核心标记 | 55.8% | 25.2% | 65.6% |
| 有 tag | 97.3% | 96.1% | 99.4% |
| 本词书对应 tag | 74.7% | 84.2% | 97.6% |
| exchange 词形 | 81.3% | 81.4% | 80.9% |
| pos | 0% | 0% | 0% |
| 例句 | 0% | 0% | 0% |
| 音频 | 0% | 0% | 0% |

**结论：**

- **词表覆盖很强。** 三本词书一个词不缺；中文释义、英文释义、音标都接近 100%。  
  这意味着 ECDICT 足以做“选词 + 基础释义 + 音标 + 难度/词频”的底座。
- **考试标签不能直接当词书。** CET4 只有 3,394 / 4,542 带 `cet4` 标签；CET6 3,362 / 3,991；高中 3,648 / 3,738。  
  你可以用它做辅助，但不能用它替代你自己的词书分类。
- **学习层是空的。** `pos` 为 0、`detail` 约 0、`audio` 为 0。  
  这三项恰好是“词卡”和“词典”的分界线。

### 1.3 和主流 App 的卡面差距

| 需要的层 | ECDICT | 主流 App 的水平 | 差距 |
|---|---|---|---|
| 单词/音标 | 强 | 百词斩、不背、墨墨都有 | 小 |
| 中文核心义 | 有，但多义项混杂、领域噪声多 | 选好 1 个核心义，按考频/场景排序 | **大** |
| 英文释义 | 有，偏 WordNet 风格 | 柯林斯/学习型词典/双语解释 | 中 |
| 词性 | CSV 为空 | 明确 pos + 义项映射 | **大** |
| 例句 | 无 | 1–3 条真实/考试例句，带翻译和音频 | **致命** |
| 音频 | 无 | 单词 + 例句原声/TTS | **致命** |
| 搭配/词组 | 无 | 不背 5 万+ 搭配；百词斩有词组 | **大** |
| 词根/词缀/词族 | 只有 exchange（屈折变化） | 不背 2000+ 词根、5000+ 派生树；百词斩有派生 | **大** |
| 近义/反义/形近 | 无结构化字段 | 百词斩、不背都有 | 中 |
| 助记 | 无 | 墨墨/百词斩有用户或编辑助记 | 中 |
| 图片 | 无 | 百词斩的核心 | 取决于你是否需要 |
| 考义/考频 | 只有词级 tag | 义项级考频、真题例句 | **大** |
| 难度/CEFR | collins/oxford/frq 可近似 | 分级词书/CEFR | 中 |
| 词形变化 | 强 | 多数 App 有 | 小 |
| 例句/音频版权 | 无 | 自有/授权 | **上线风险** |

一句话：**ECDICT 能让你做出“带音标和中文释义的 Anki 式卡”，但做不出百词斩/不背/墨墨那种“学习型卡”。**

### 1.4 ECDICT 的四个硬伤

1. **没有例句。**  
   `detail` 是空的；`definition` 是词典释义，不是例句。没有例句，就没有“词在句子里怎么用”的锚点。

2. **没有音频。**  
   `audio` 为空。你只能用浏览器 TTS 或外部 TTS；音质、口音、连读都不稳定。

3. **没有义项排序。**  
   `translation` 的第 1 行不一定是核心义。  
   例如 `charge` 第一条是“指控”，`fine` 第一条是“罚款”，`mean` 第一条是“低劣的”；直接取第一行会做出“词典卡”，不是“学习卡”。

4. **没有教学层。**  
   没有“这个词在考试里最常考哪个义项”“这个词和哪个词容易混”“这个词的搭配是什么”。  
   这些恰恰是主流 App 花最多人力打磨的部分。

### 1.5 版权

ECDICT 仓库是 MIT License，但数据来源包含 cdict、WordNet、BNC、考试词表、网友贡献等；**MIT 是仓库声明，不等于所有上游内容都没有第三方权利**。  
公开上线前需要逐项确认；例句、音频、图片、歌词的版权风险更高。

## 2. 词卡产品模型

### 2.1 一张卡不是一张卡，是一条卡链

主流 App 真正有效的不是“卡面”，而是**同一词在不同阶段的不同任务**：

| 阶段 | 卡型 | 正面 | 背面 | 目的 |
|---|---|---|---|---|
| 初见 | 语境卡 | 歌词/例句 + 单词 + 音频 | 核心义 + 一句解释 | 建立理解和情绪连接 |
| 学习 | 回忆卡 | 单词 + 语境，释义藏起 | 释义 + 例句 | 主动提取 |
| 巩固 | 挖空卡 | 歌词/例句挖掉目标词 | 目标词 + 音频 | 形式与语境绑定 |
| 听辨 | 听音卡 | 只放音频 | 单词 + 释义 | 听觉表征 |
| 产出 | 拼写/造句卡 | 中文义/音频 | 拼写/说出/造句 | 产出性知识 |

橙记现在做的是第一层“语境认词卡”，做得很好；缺的是第二层“回忆卡”和第三层“挖空/听辨/产出”。

### 2.2 一张卡的最小字段

建议未来卡的数据模型至少包含：

```text
word, phonetic, pos
coreSense（1 个核心义）
secondarySenses（可选，最多 2 个）
example { en, zh, audio, source, license }
collocations（1–2 个）
wordFamily（可选）
rootOrMnemonic（可选）
tags { exam[], cefr, collins, oxford, bnc, frq }
context { lyric?, songId?, audio?, start?, end? }
qualityTier A/B/C
reviewStatus
sourceLicense
```

原则：

- **一张卡只考一个义项。**
- **正面不要把所有东西摊开**；词根、派生、近义放第二层。
- **例句必须包含目标词**，且翻译准确；否则不是例句，是装饰。
- **音频必须和词/例句对得上**；TTS 也要标 provider。
- **每个字段记录来源和许可证**；上线时能追溯。

### 2.3 内容分级：不要假装 77 万词都一样

| 层级 | 范围 | 内容 | 生产方式 | 目标 |
|---|---|---|---|---|
| A | 3,000–5,000 核心/高频/考试词 | 核心义 + 1–2 例句 + 音频 + 搭配 + 考义 | 人工审核为主，ECDICT 打底 | 对标主流 App |
| B | 10,000–20,000 次高频 | 核心义 + 例句 + TTS + 基础搭配 | 自动 + 抽检 | 可用、可扩展 |
| C | 长尾 | 词 + 音标 + 中文释义 + 词形 | ECDICT 直出 | 查得到、能认 |

**首发不应该做 77 万张卡。**  
先把 A 层做扎实，B 层自动化，C 层诚实标注“基础卡”；这比“全库都有例句”更可信。

### 2.4 内容来源与许可证

| 内容 | 可用来源 | 注意 |
|---|---|---|
| 词表/释义/音标/词频/考试标签 | ECDICT（MIT） | 上游版权需复核；清洗义项 |
| 英文释义/近义/派生 | WordNet（Princeton 许可） | 需保留许可声明 |
| 例句/翻译 | Tatoeba（CC BY 2.0）、Wiktionary（CC BY-SA） | 需要署名/相同方式共享；质量参差 |
| 例句/翻译（备选） | 自建语料、授权真题、LLM 生成 + 人工审 | LLM 要标注、抽检；不要用于法律/医学 |
| 音频 | 浏览器 TTS、云 TTS、Wiktionary/Forvo（授权） | 原声最好，但版权/成本高 |
| 词根/词源 | Wiktionary、Etymonline（授权） | 词根解释常有附会，标注“助记”而非“真理” |
| 搭配 | 语料库/LLM/人工 | 需要频率和自然度校验 |
| 图片 | 自有/授权图库 | 不是必须；与两色设计可能冲突 |
| 歌词/歌曲音频 | 用户自有平台/授权 | **公开上线最大风险** |

## 3. 智能调度与分发

### 3.1 抖音算法开源了吗？

**没有开源。**  
公开可见的是：

- TikTok 对推荐系统的公开说明；
- 字节跳动 2022 年的 Monolith 论文（实时训练、无冲突 embedding table）；
- 大量第三方对多阶段推荐架构的分析；
- 泄露文档/传闻，不能当官方实现。

可以确定的骨架是：

```text
候选召回 → 多目标排序 → 重排/多样性/探索 → 实时反馈 → 下一轮
```

但**具体模型、特征、权重、目标函数是商业机密**。不要按“泄露公式”去实现；可以按这个骨架做自己的小系统。

参考：[Monolith 论文](https://arxiv.org/abs/2209.07663)

### 3.2 可以融合的部分：调度与分发解耦

```text
记忆层（FSRS）
  → 今天到期的词 / 学习中 / 新词
  → 每个词的可选语境（歌、歌词、例句、音频、题型）
  → 分发层（规则 / bandit / ranker）
  → 会话编排（上限、多样性、难度、时长）
  → 用户行为
  → 更新记忆状态 + 语境偏好
```

- **记忆层**回答：这个词现在该不该复习？  
- **分发层**回答：用哪首歌、哪条例句、哪种题型，让这次复习最可能被接受、最可能形成有效提取？  
- **会话层**回答：今天做多少、什么时候停、如何避免“信息流无限”。

这才是“抖音 × Anki”的正确接口。不是让抖音算法去决定“这个词该不该复习”，而是让它决定“怎么端上来”。

### 3.3 不能融合的部分

- **不能用停留时长作为目标。**  
  抖音优化时长是因为广告；学习优化时长会奖励“简单词、娱乐内容、重复已会词”。
- **不能用“完播率”直接代替回忆。**  
  看完≠记住；听完≠会。
- **不能无限流。**  
  学习需要停止点；每日新词/复习上限、完成态、休息提示必须保留。
- **不能只推用户喜欢的语境。**  
  只推熟悉歌曲会形成“舒适区”，降低提取难度；需要探索和多样性。

### 3.4 信号与奖励

| 信号 | 能推断什么 | 风险 |
|---|---|---|
| 是否点开释义 | 是否认出 | 可能只是好奇 |
| 点“认识”前的延迟 | 提取难度/犹豫 | 可能走神 |
| 重播歌词/例句 | 情感编码/理解需求 | 也可能只是好听 |
| 跳过/快速滑走 | 太简单/太熟/厌烦 | 也可能是误触 |
| 评分（忘记/模糊/认识） | 主观回忆 | 自评会失准 |
| 7 天后在新语境中认出 | 真实迁移 | 最强，但来得慢 |
| 30 天保留率 | 长期效果 | 更慢 |

**北极星指标建议：**

> 7 天后，到期词在**新语境**（另一首歌/另一条例句）中的无提示回忆率。

辅助指标：

- 30 天保留率；
- 首次回忆时间；
- 提示/重播率；
- leech 率；
- 新词毕业率；
- 会话完成率；
- 每日学习时长（只做约束，不做目标）。

**不要**把 DAU、停留时长、连续天数作为北极星。

### 3.5 MVP 调度器：FSRS + 规则 + 轻量 bandit

**第一版不需要机器学习排序。**

1. **记忆层**：保留现有 FSRS（`ts-fsrs`），不重写。
2. **评分**：至少三键——**忘记 / 模糊 / 认识**。  
   现在只有“模糊/认识”，等于只有 Hard/Good；没有 Again。  
   代码里 `Grade3` 已经支持 `again`，UI 没暴露；这是最便宜、收益最大的修复。
3. **当天修复**：忘记后，在本次会话隔 2–3 张再出现一次；模糊可以晚一点再出现。  
   这不改 FSRS，只在 session 层做 requeue。
4. **leech**：同一词连续失败达到阈值（Anki 是 8 次 lapse），暂停/换卡/降级，而不是无限重复。
5. **会话配比**：到期优先；建议从 70% 到期 / 20% 临期 / 10% 新词或探索开始，但这是启发式，必须 A/B。
6. **分发层**：先规则——  
   - 优先用户最近常听的歌；  
   - 同一首歌一天不超过 N 次；  
   - 同一词不在短时间内重复同一语境；  
   - 10% 探索：换一首歌/换一种题型。
7. **升级路径**：当有足够数据，再做 contextual bandit（Thompson sampling）或 learning-to-rank；不要一上来做深度 RL。

### 3.6 冷启动

- 不要问“你认识哪些词”——自评不可靠。
- 用 20–30 个**有对错**的小题做分级，覆盖不同词频/词族；根据正确率、反应时、提示次数估计起点。
- 用 ECDICT 的 `exchange`/lemma 做词族迁移（认识 sail 不代表认识 sailing，但同族词可共享先验）；不要只靠词向量。
- 新用户先给高频/高价值词，不要随机撒 77 万词。

### 3.7 实验设计

先做小实验，不要先做平台：

| 实验 | 对照 | 指标 |
|---|---|---|
| 三键 vs 两键 | 忘记/模糊/认识 vs 模糊/认识 | 7 天延迟回忆、leech 率 |
| 当天修复 vs 不修复 | 忘记后 session requeue | 当天二次正确率、7 天保留 |
| 歌词语境 vs 文本例句 | 同词不同语境 | 新语境回忆率、偏好 |
| 挖空 vs 普通认词 | 歌词挖空 | 形式回忆、拼写 |
| 10% 探索 vs 0% | 换歌/换题型 | 7 天保留、次周留存 |
| 分发排序 vs 随机 | 偏好模型选语境 | 完成率、延迟回忆 |

样本量不用一开始追求论文级；先看方向和效应量，再扩大。

## 4. 执行顺序（HAA 冲刺见 `docs/haa/sprint-7-days.md`）

1. **卡契约**：确定认词/产出目标、三种卡型、三键语义、音频粒度。
2. **200 词切片**：一本真实词书、真实例句、TTS、人工审义；先证明内容管线。
3. **卡链 v0**：context / recall / cloze，三键，忘记同卡重试，FSRS 不变。
4. **公开 demo**：GitHub Pages 静态部署，去掉需要 API 的 tab。
5. **5–10 人试用**：看 7 天延迟回忆和定性反馈，不追求大样本。
6. **再扩内容**：A 层 3,000–5,000 词；B/C 层自动 + 抽检；最后才做分发/bandit。

## 5. 风险与决策点

1. **内容版权**：歌词/音频/例句/图片，哪一个能公开分发？  
2. **音频质量**：TTS 够不够？要不要为 A 层买真人音频？  
3. **产品目标**：阅读/听力（认词）还是写作/口语（产出）？决定卡型比例。  
4. **首发范围**：3,000 词精品 vs 77 万词词典？建议前者。  
5. **数据位置**：本地 IndexedDB 还是账号云端？多设备/多用户需要后端。  
6. **算法伦理**：是否愿意把“停留时长”从目标里拿掉？这是产品价值观问题。  
7. **失败定义**：用户点“模糊”到底是“想起来但费力”还是“忘了”？必须统一，否则 FSRS 会被污染。

---

## 6. 不要做

- 不要把 ECDICT 第一行释义直接当卡。
- 不要用 `collins` 星级代替完整词典内容。
- 不要在没有例句/音频的情况下宣称“对标百词斩/不背”。
- 不要用停留时长做北极星。
- 不要在没有 7 天延迟数据前上复杂排序模型。
- 不要把“认识”做成唯一评分；没有 Again，就没有失败信号。
- 不要用自评替代客观小测；也不要用客观小测替代真实语境。
- 不要忽略歌词/音频/例句的版权。
